# Development Workflow

## PR 同步与冲突处理

当前仓库采用分阶段实现方式：先合并项目骨架，再在骨架之上继续实现后端 API。后续开发分支应始终基于已经合并的最新主干提交创建，避免在同一个 PR 中重复提交已合并的目录结构或文档改动。

处理 PR conflict 时建议遵循：

1. 先同步最新主干分支。
2. 保留已合并的项目结构约定：`backend/`、`web/`、`desktop/`、`mobile/`、`docs/`。
3. 对同一文档的冲突，保留主干已有架构说明，并叠加当前功能分支新增的实现状态。
4. 对后端代码冲突，以后端 API 作为唯一数据源的原则为准，不允许客户端绕过后端直接访问数据库。
5. 冲突解决后至少运行 `cd backend && npm test` 与 `git diff --check`。

## 当前实现基线

本分支在已合并的项目骨架上继续实现后端 API 原型，当前需要保留：

- 根目录多端结构与文档入口。
- `backend/src/routes.js` 中的统一 `/api/v1` 路由。
- `backend/src/modules/*/service.js` 中五个优先模块的处理逻辑。
- `backend/test/api.test.js` 中覆盖核心业务链路的集成测试。


## 中文规范

后续代码注释、提交信息、PR 标题和 PR 描述统一使用中文。外部协议名、接口路径、技术名词和代码标识符可保留英文原文。
